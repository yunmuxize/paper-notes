## 0. 一句话总结

**把性能剖析逻辑本身编译成轻量级 GPU 探针内核，让它成为执行图里的普通节点**——剖析不再从外部打断异步执行流，而是成为异步流的一部分，从而做到常开、内核级、<1% 开销的实时追踪。

与 SiPipe（上一份笔记）恰好互补：**SiPipe 用空闲 CPU 填 GPU 气泡，LMTracer 用不扰流的探针看见 GPU 气泡**——一个解决，一个观测，两者共享同一个核心认知：GPU 的高效来自"无屏障的异步流水"，任何从外部插入的同步点都是性能敌人。

## 1. 研究问题：为什么需要"常开的内核级 profiler"

**问题**：生产 LLM 系统（训练数千卡×数周、服务延迟极敏感）需要**始终开启**的性能监控，在退化发生的当下定位根因；但现有工具要么太粗、要么太贵，没法常开。

**为什么重要**：能实时回答"哪一层变慢了 / 哪个 GPU 拖尾了 / 是不是 NVLink 降速了"，不用停服排查。论文的收益证明：修复 15 个只有常开追踪才能捕获的问题后，**服务延迟降 21.2%，吞吐升 24.5%**——"可观测性本身就是性能优化"。

**观测者效应（问题的本质）**：明明知道系统在变慢，但一开 profiler，系统就不慢了——profiler 自己把系统拖慢 10%–80%，原本的微妙瓶颈被 profiler 的扰动淹没。测量的行为改变了被测量的系统。

## 2. 现有方案的三档缺陷（按理解重组）

| 档位 | 代表 | 能看到什么 | 结构性缺陷 |
|---|---|---|---|
| 框架/遥测指标 | vLLM/SGLang 吞吐、迭代时间；eBPF(CPU侧) | 系统级信号 | 太粗：低吞吐无法区分是内核低效、调度不均还是网络瓶颈。适合告警，不适合调优 |
| 厂商内核剖析器 | CUPTI、Nsight Systems | GPU 内核时间线 | ① **语义黑盒**：CUDA Graph/Inductor 融合后只剩 `ampere_bf16_s1688gemm`，不知道对应 MLP 上投影还是下投影；② **开销大**：CUPTI 训练 70B 退化 5.2%（服务 9.1%），PyTorch Profiler 服务场景吞吐掉 83.4% |
| 运行时事件 | CUDA Events 手动插桩 | 精确的时间点 | 要改代码；**Event 不能参与内核融合**——插一个 Event 就把可融合的算子拆开、执行图被屏障打断，开销超 12%，与图执行不兼容 |

**共同根源（结构性矛盾，全文最核心的洞察）**：所有现有剖析手段都依赖某种**屏障（barrier）**保证数据对齐；而 LLM 的 GPU 执行之所以高效，恰恰因为**没有屏障**——CPU 非阻塞发射内核、GPU 在内核之间零空闲连续执行、内核融合成图、图一次发射重放。在异步流里插一个同步点，异步流就断了。

## 3. 核心思想（Intuition）

**推理链**（DeepSeek 重建的作者思考路径）：

1. profiler 重，不是因为记录时间戳重——读一次 GPU 时钟寄存器是纳秒级操作；**重的是同步**。CUPTI 为了时间线准确，必须建立屏障让 GPU 停下来刷数据、对齐、再继续。
2. 反问：如果记录时间戳的不是"运行时事件"，而是**一个内核本身**呢？内核是 GPU 的基本执行单元——把它和用户内核一起发射、一起被捕获进 CUDA Graph、一起按序执行，它就天然是异步流的一部分，**不需要任何屏障**。
3. 数据怎么回 CPU？不能让 GPU 等读——GPU 写进自己管理的影子缓冲区，写满发一个"门铃"信号，CPU 异步来拉，GPU 不等确认。

**一句话本质**：不要试图让剖析"不干扰"执行，而是**让剖析成为执行的一部分**。不是在异步流外面架摄像机，而是在流里面放一个乘客——乘客不会让列车停下来，只要有自己的座位（影子缓冲区）和不阻塞上下车的协议（门铃信号）。

**类比**：传统 profiler = 高速公路设检查站，每辆车停车交费，交通流被打断；LMTracer = 每辆车装 ETC 标签，行驶中自动扣费，收费站（CPU）异步对账。

## 4. 方法 Pipeline（以 SGLang 中剖析 RMSNorm 为例）

**输入**：YAML 配置指定要剖析的函数（`sglang.srt.layers.layernorm.RMSNorm.forward_cuda`）及可选代码行范围，一次性配置。

![LMTracer Listing 1：剖析配置示例——模块/函数/代码行级探针 + 文件与 Prometheus 两种导出器](figures/listing1_yaml_config.png)

**四步**：

![LMTracer Figure 5：架构总览——剖析配置 → 栈感知编译 → 执行器绑定 → GPU 执行+影子缓冲异步回传 → 导出 → 瓶颈分析](figures/fig5_architecture.png)

### 4.1 栈感知编译（Stack-Aware Compilation）——决定探针插哪里

- 关键难题：内核融合让 GPU 执行变成黑盒。要知道 fused kernel 里哪一段对应你的 RMSNorm，**不能靠运行时猜（内核名/张量形状都不可靠），必须在编译时静态建立映射**。
- 机制：hook 进 `torch.compile` / Inductor 的编译过程，**递归回溯每个融合内核里每个算子的静态调用栈**；若某算子的调用栈与用户配置的代码区域相交，就在**融合内核的边界**插探针（而不是在用户代码行之间强行切开——探针不是可融合的算术算子，插进内核内部会破坏融合）。

![LMTracer Figure 6：栈感知编译——彩色箭头标出"源代码 → 算子调用栈 → 融合内核"的映射，探针插在覆盖目标区域的内核边界](figures/fig6_stack_aware.png)
- 探针做的事极轻：在目标内核执行前后读 GPU `globaltimer` 寄存器（AMD 为 `s_memtime`），两值相减即执行时间。**不修改用户内核的任何指令、寄存器或共享内存状态**，保真度不受影响。

### 4.2 探针合并——减少探针数量

- 两个探针落在同一内核边界（如 Attention 的退出探针和 Norm 的进入探针在同一边界）→ 合并为一个、分配新哈希 ID。
- 消融证据：关闭合并后吞吐退化从 0.9% 跳到 2.9%–3.0%——**探针插入位置对执行行为是敏感的**（这一点后来成为最脆弱假设的证据）。

### 4.3 门铃辅助影子缓冲（Doorbell-Assisted Shadow Buffering）——数据怎么出来

- GPU 侧两个影子缓冲区 A/B：探针往当前缓冲区写（时间戳 + trace point 哈希 ID），写满后向一块 CPU-GPU 映射内存写**门铃**信号，切到另一个缓冲区继续写。
- CPU 侧轮询线程监听门铃，看到信号就在**独立 GPU 流**里异步拷走满缓冲区；探针完全不受影响，继续写另一个。
- 一致性：探针更新门铃前执行 `__threadfence_system()`（release-acquire 顺序），保证之前的缓冲区写入对 CPU 可见。

![LMTracer Figure 7：门铃辅助影子缓冲——GPU 写满一块就响铃，CPU 在独立流里异步拉走，探针不停写另一块](figures/fig7_doorbell.png)

### 4.4 执行器绑定与图兼容——怎么透明地塞进用户进程

- 利用 Python site-specific 配置钩子监测包导入事件，自动找到 vLLM 的 Worker 类 / SGLang 的 ModelRunner 类，在 executor 初始化前打 patch。
- 探针内核被驱动当普通内核，在 **warm-up 阶段一起被捕获进 CUDA Graph**，图重放时无缝执行——这是"图兼容"的关键：探针不增加图边界。

**输出**：二进制 trace → 文件 / Prometheus / Flink；重建内核间 wait-for 依赖、计算 GPU 气泡占比、识别 straggler GPU、映射回用户代码行。

![LMTracer Figure 8：被剖析的推理流水线示例——A=attention、M=MLP、L=decode 层、S=sampling](figures/fig8_pipeline.png)

## 5. 核心数学：GPU 气泡占比（全文唯一的公式）

$$\text{BubbleFraction} = 1 - \frac{\sum_{i=1}^{N} d_i}{t_N - t_1 + d_N}$$

从零理解：监控窗口内 GPU 执行了 N 条记录。$t_1$ 是首条记录开始时间，$d_i$ 是第 i 条持续时间，$t_N$、$d_N$ 是末条的。**分子** ∑dᵢ = GPU 真正干活的总时间；**分母** = 首条开始到末条结束的总墙钟窗口。忙碌占比取补即空闲（气泡）占比。

直觉：GPU 不间断时分子趋近分母，气泡趋近 0；等待通信 / 等 CPU 发射 / 等调度器分配的停顿计入分母却不计入分子，气泡上升。

**妙处**：这个指标不告诉你气泡的**成因**，只告诉你"这里有空闲"——成因要再用 trace 数据下钻到内核级看。论文图 16 的"不均衡调度"案例中它自动告警：请求被不均匀路由到不同 PP 实例，部分 GPU 在气泡里空转。

## 7. Takeaways

1. **剖析的敌人不是"采集"，是"同步"**。读时钟是纳秒级操作，CUPTI 的开销几乎全来自对齐时间线的屏障。把剖析做成内核融入异步流，同步需求就消失了。
2. **栈感知编译解决"语义锚定"**。内核融合制造黑盒；编译时调用栈是唯一可靠的语义映射来源，运行时猜测（内核名、张量形状）都不可靠。
3. **生产可观测性的正确形态是"常开追踪"而非"按需剖析"**。按需剖析只能抓到你怀疑的东西；常开追踪能抓到你**不怀疑但实际在拖慢系统**的东西——15 个问题里 9 个属于此类。
4. **0.9% 不是理论下限**。后续 SysOM-AI 用 eBPF 做到 <0.4%；LMTracer 的独特位置在"内核级语义保真度"，不在绝对开销。

## 8. 批判性视角

### 8.1 最脆弱的假设

**"探针内核不扰动执行图的行为"能否推广到所有异步执行模式。** 论文验证集中在 CUDA Graph 捕获-重放场景（探针 warm-up 时一起捕获、图内按序执行、不增加图边界）。但有三个未充分验证的缝隙：

- **图边界固有停顿**：TornadoVM 实测即使不剖析，CUDA Graph 边界本身就有 GPU 空闲（A10 上每边界约 210µs；Gemma 4 31B decode 每 token 约 7 个边界 ≈ 3ms 空闲）。探针不增加边界，但若探针的存在**改变了图的结构**（如阻止某种跨边界融合）或其内存流量在带宽受限时与下一图内核启动竞争，0.9% 就要逐场景重验。
- **融合模式同构性**：消融显示关闭探针合并开销跳到 3%，说明插入位置敏感；生产负载的融合模式未必与论文测过的 Qwen/DeepSeek 同构。
- **缓冲区假设的边界**：1MB 缓冲">200 次迭代"是在 671B 模型、探针数有限的条件下成立；探针粒度推到每层每算子，翻转频率线性增长，门铃频率随之增长。

### 8.2 反例设计（如果我要反驳它）

核心逻辑：**构造"探针与用户内核按序执行"在代价上不再中性的负载**。

![LMTracer Figure 16：不均衡用户请求调度示例——Bubble Fraction 自动告警的典型案例](figures/fig16_unbalanced.png)

- **计算-通信深度重叠**：PP=4、TP=8、micro-batch 极小，AllReduce 与下一 micro-batch 前向几乎完全重叠。NCCL 通信内核不是 Inductor 生成的融合内核，栈感知编译不会在其边界插探针 → 探针只见计算侧时间，**看不到计算-通信重叠边界**；若剖析区域横跨两者，边界选择可能切开重叠窗口或无法归因通信等待。
- **门铃风暴**：影子缓冲接近满时注入高频探针，观察 CPU 轮询线程在多进程高竞争下是否调度抖动，让"异步拷贝"在 **p99** 上退化成同步停顿——均值 0.9% 不代表尾部不打扰。

### 8.3 一周最小复现

验证 claim："探针内核可被 CUDA Graph 捕获，且不破坏原始图执行的迭代时间。"

做法：vLLM/SGLang 跑 7B–8B 模型 decode，固定 batch 和生成长度，开/关 LMTracer（只剖析一个最小阶段）各测一遍迭代时间分布 + nsys trace。判定：(a) 中位数与 p99 退化 <1%；(b) 图边界数量与边界空闲时间无变化——若边界空闲被放大，说明探针虽无屏障但改变了图结构，0.9% 在该负载不成立。代码已开源、支持自动 hook，单卡 + nsys 即可。

## 9. 后续研究与新认知

**方向一：跨层、集群级持续诊断，开销压得更低。**
- **SysOM-AI**（阿里，80,000+ GPU）：eBPF 做 CPU 栈剖析 + NCCL 事件插桩 + GPU 内核追踪，<0.4% 常开开销，诊断 94 个生产问题，中位诊断时间从数天压到约 10 分钟。
- **ARGUS**（10,000+ GPU）："CPU 调用栈 + 框架语义 + GPU 内核执行"分解式追踪，<2% 开销，原始事件压缩约 **3,700 倍**（每 rank 每 step 10MB→2.7KB），能自动区分"计算 straggler"与"被通信症状掩盖的计算 straggler"。
- 启示：LMTracer 的探针内核路线在内核语义保真度上强，但生产需要的是把 CPU 阻塞、NCCL 等待、GPU 停顿放上**同一条时间线**——系统栈覆盖广度上它不是终局。

![LMTracer Figure 15：剖析保真度对比——LMTracer 能还原 RMSNorm 等 Triton 融合区域的语义，Nsight 只有黑盒内核名](figures/fig15_fidelity.png)

**方向二：CUDA Graph 自身的异步性成为独立瓶颈，反过来暴露"图内探针"的边界。**
- TornadoVM PR：不剖析的情况下，连续发射 CUDA Graph 的图边界空闲可达每 token 约 3ms；修复 = 异步发射下一图不等上一图，Gemma 4 31B decode 的无内核 GPU 空闲从 192.6ms 降到 57.9ms。
- 启示：图内探针采集的时间线会把**图边界停顿算进气泡占比**，用户可能误以为气泡是探针造成的——实际它是 CUDA Graph 执行模型的一部分。

**新认知**：LMTracer 的真正贡献不是"0.9% 最低"，而是**证明了"把剖析逻辑编译成执行图节点"这条路可行**，且栈感知编译是解决内核融合语义丢失的正确抽象。后来者仍要面对同一个问题：如何在不打断异步流的前提下对齐 CPU-GPU 因果关系。

## 10. Follow-up Idea（对话中提出，非增量）

**缺口**：探针是**静态**的——编译期定位置、运行时固定频率写。但生产瓶颈动态漂移：batch 组成变了，瓶颈从注意力内核移到 AllReduce；NVLink 降速，气泡从 PP 边界移到 DP 边界。静态探针在瓶颈转移后仍采集同样的位置——无关 trace 数据大量产生，新瓶颈位置却无覆盖。ARGUS 的 3700 倍压缩是**采集后**做减法，更根本的浪费在**采集前**。

**Idea：基于在线依赖分析的探针动态重配置（Adaptive Probe Reconfiguration）**。用 LMTracer 已采集的内核间 wait-for 依赖图作在线信号，实时算每个探针位置的"边际信息量"：连续多窗口与上下游高度共线 → 降采样/移除；周围出现新气泡或 straggler 依赖 → 提采样率、把探针临时迁移到未覆盖的边界内核。探针的插拔/重定位不需重编译内核——利用 CUDA Graph 条件节点，或仅在探针拓扑变化时触发一次图重捕获（频率远低于迭代频率）。

**为什么不是增量**：把探针本身变成**运行时自适应资源**，回答 LMTracer 没回答的问题——瓶颈拓扑迁移时，常开追踪如何把有限探针预算重分配到最有信息量的边界。需求真实：LMTracer 自己报的 15 个问题（KV cache 驱逐、预填充阻塞、RNIC 抖动）全是间歇性、非平稳的，静态覆盖在时间维度上非最优。

**技术难点与折中**：CUDA Graph instantiate 是毫秒级，重配置必须限频并在窗口内保持数据连续。可能方案：**分层探针**——一组低频基础探针覆盖全图 + 一组高频"机动探针"（位置由在线依赖分析决定，主机侧异步重定位、不触发全图重捕获）。本质是把追踪形式化为**在线实验设计**：每轮采样都在决定下一个最有信息量的观测点。
